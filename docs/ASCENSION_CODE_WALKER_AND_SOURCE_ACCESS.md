# ASCENSION Code Walker + Authorized Source Access

## Purpose

ASCENSION must be able to work from a person's actual authorized state instead of requiring them to manually re-enter everything every time.

The Library Card is completed before the personalized ASCENSION experience begins. It is not the Book's job.

- General question: Library Card is optional; basic/general pathway access is allowed.
- Personalized pathway, Destiny, objective, execution, or capability-extension work: Library Card is required first.

The Book remains the gateway into the experience:

`Book → command/objective → ENGAGE → pages flutter/open → Tree of Knowledge → Knowledgeverse / pathway construction`

## Authorized source layer

ASCENSION may use only sources the person explicitly authorizes. Supported source classes are modeled as:

- file system / folders
- repositories
- applications
- game projects
- plugin or scripting APIs
- runtimes
- devices
- cloud services

Permissions are explicit and independent:

`read | search | write | create | execute | control`

Missing permission is never inferred as granted permission.

Authorized sources feed the person's current-state model and Library Card. Source observations remain distinct from ASCENSION VERIFIED / PERSISTED state until governed verification accepts the resulting change.

## Read and act are separate capabilities

### Read / inspect

ASCENSION can search and inspect authorized files, documents, project structures, configurations, assets, logs, APIs, plugins, runtime state, and connected services.

### Act / control

Where explicit permission and an execution interface exist, the ASCENSION runtime / ExecutionEngine can create, edit, move, or connect files; invoke supported app/plugin/API operations; launch supported build/test paths; and execute the selected pathway.

The web answer layer does not pretend those actions happened. Device/app/file actions require an authorized runtime receipt.

## Code Walker

Code Walker is the ASCENSION capability-discovery and extension pathway for an existing software environment.

It does not treat the target like a blank project. It enters the existing authorized system, learns how it works, finds the narrowest supported extension point, changes only what is required, and proves the result against the real runtime.

Canonical sequence:

`Authorized system → enter → trace architecture → map dependencies/data/control flow → locate extension point → add/connect capability → build/run/test → observe actual behavior → AutoSync/governed verification → verified change → Δ / Library Card update`

Code Walker traverses more than source code:

- code
- APIs
- plugins
- project files
- configs
- assets
- runtime state
- logs
- permissions
- connected services

## Games

### Project/source access

When the person owns or is authorized to modify the project, Code Walker can map the engine/project architecture and route the capability into the real project through supported extension points.

Examples include mechanics, NPC behavior, UI, quests, abilities, inventory, procedural systems, AI companions, accessibility, and other project-level features.

### Installed-only access

If only the installed game is available, Code Walker is limited to extension surfaces the game actually exposes, such as:

- official mod APIs / SDKs
- plugin APIs
- scripting APIs
- save/config interfaces
- telemetry
- overlays
- companion-app APIs

Bypassing anti-cheat, authentication, access controls, or other protections is not a valid Code Walker extension point.

## Verification boundary

A proposed code change is not a completed capability.

Required evidence chain:

`Possible → Simulated → Recommended → Selected → Executed → Verified → Persisted`

Code Walker can map and plan before execution. A capability can only be called added after the authorized runtime executes it, the real system is observed, and the governed verification chain accepts the evidence.

## Product relationship

`Authorized sources → Library Card/current state → Book/objective → Knowledge Retrieval + Code Walker/capability selection → DTF pathways → selected pathway → ExecutionEngine across permitted systems → observed evidence → AutoSync/Guardian verification → Δ → Library Card/current state update`
